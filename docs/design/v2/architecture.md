## 〇、11-05 实测（定架构用的事实）

| 事 | 结果 | 怎么测的 |
|---|---|---|
| Claude Code 命令行在本机能不能「接着上次的会话说」 | **能**：`--session-id <uuid>` 开新会话，`--resume <id>` 接着说（记得上一句里的暗号），`--resume <id> --fork-session` 分叉出新会话（分叉后原会话不受影响：原会话里再问「我发了几条」答 3） | 本机 `claude -p`，空临时文件夹，零工具，4 次真调用（脚本在玄翎的 scratchpad：resume-spike.mjs） |

| v1.0 调 Claude Code 的方式 | 零工具 + `--no-session-persistence`（每次一问一答、不留会话） | `core/src/connect/claude-code.mjs` 第 34–41 行 |

## 一、总图：三层 + 两个进程

```
┌────────────────────────── 流息桌面应用（Electron） ──────────────────────────┐
│ 页面（renderer）：左栏 B · 库架 · 和主 Agent 聊 · 库页五标签 · 设置            │
│        │ 只经「桥」（preload，方法表三处一致，v1.0 的规矩）                      │
│ 主进程（main）：库登记 · 定时与排队 · 主 Agent 对话 · 提议卡 · 建议卡 · 桥服务    │
│        │ 调用                                                                │
│ 核心（core，纯 Node 零依赖，自己的测试）：库 · 抓取 · 流水线 · 核验 · 问库 ·     │
│        连接 · 【新】agent · 【新】proposals · 【新】suggest · 【新】registry     │
│        │ 子进程 / HTTPS                                                       │
│ 连接：连接你电脑上的 Claude Code / Codex（命令行子进程）· API key（HTTPS）        │
└──────────────────────────────────────────────────────────────────────────────┘
磁盘：<应用数据>\Streams\（设置、主 Agent 的对话与工作区、各库登记）  +  每个库自己的文件夹（v1.0 的格式，加几样）
```

三层分工（设计稿第二节，不变）：

| 层 | 在代码里是什么 | 模型调用方式 | 能动什么 |
|---|---|---|---|
| 主 Agent | `core/src/agent/`：一个长对话；对话记录流息自己存一份（正本），命令行会话 id 只是加速用的缓存 | 每一轮：流息把「当前局面摘要」+ 你这句话交给模型，要求按 JSON 格式回：`{ reply, ask?, proposals[], lookups[] }`；`lookups` 是它想看的东西（某库的概况、某来源的抓取记录），代码查好再喂回去，最多 3 次 | **只能出提议卡**（`proposals`），由代码校验、等你确认、再由代码执行；没有 shell，不能读写任意文件；它的「工作区」= 流息给它存的笔记（`agent/notes.jsonl`，也经代码写） |
| 库 Agent | v1.0 流水线里的那些调用：两道关打分、摘要、核验，按库的「要求」组织提示词 | 每条 / 每批一次零工具调用（v1.0 原样），**不留会话**（读的是网上内容，不让它记事也不让它动手） | 只交结构化结果；代码写账本 |
| 问库 | v1.0 `core/src/ask/` + 新的「分流」一步 | 零工具、不留会话 | 只答；判成「改动要求」的转给主 Agent |
| 流息的代码 | 抓取、去重、账本、写盘、定时、试抓、执行已确认的提议、规则型建议 | 不调模型 | 全部写盘都在这里 |

**为什么主 Agent 用「JSON 动作」而不是让命令行自己调工具**：三种连接（Claude Code、Codex、API key）用同一套办法；命令行照旧零工具（v1.0 的安全约定不破）；动作是数据，代码逐条校验、能测、能重放。代价：主 Agent 想看东西要绕一次 `lookups`（最多 3 次，超了就照现有信息答）。

## 二、后台：模块清单

### 2.1 照搬 v1.0（改动小）

| 模块 | v1.0 位置 | v2 改什么 |
|---|---|---|
| 库的文件格式、`writeNoteFile`（V2 的唯一写入口） | `core/src/library/` | 不改；`streams.json` 多三个字段：`brief`（这个库的「要求」一段话）、`schedule`（这个库的定时，原来在应用设置里）、`cap`（每轮上限，原来是全局） |
| 抓取：RSS / Atom、arXiv、Hacker News、手动投入，五种状态，`fetch_log` | `core/src/fetch/` | 不改 |
| 流水线：抓 → 去重 → 关卡① 相关度 → 关卡② 实质 → 摘要 → 核验 → 待看；每轮上限、断点续跑、`rounds.jsonl` | `core/src/pipeline/` | 提示词里加上库的 `brief`；`runRound` 改成按库的 `cap` |
| 核验层（规则项 + 判定项，最多两轮） | `core/src/verify/` | **加一条规则**：材料里有写给 AI 的指令（「忽略之前的要求」「你现在是…」之类的固定模式 + 判定项兜底）→ 条目标「这一条里有写给 AI 的话，已忽略」，并给来源记一笔（UC5） |
| 问库（候选挑选、出处核对、`demand.jsonl`） | `core/src/ask/` | 前面加「分流」：一句话是提问还是改动要求（先用规则：含「以后 / 追踪 / 加 / 删 / 别再 / 改成」等再交模型判；判定结果带置信度，拿不准就问你「这是要改库吗？」） |
| 连接：三种连接、两个模型槽、登录检测、用量记账 | `core/src/connect/` | Claude Code 连接加一个「会话模式」（只给主 Agent 用）：`--session-id` / `--resume`，**仍然零工具**；Codex 的会话模式等装上实测；API 连接的会话 = 流息自己重放对话记录 |
| 首次设置「谁定的」、连续三轮没有产出、许可证页、三套主题、托盘与定时、自动更新、安装包 | 各处 | 主题、托盘、更新、安装包照用；「谁定的」扩成每次改动都记（含「主 Agent 提的 · 你确认的」）；首次设置改造见第三节 |

### 2.2 新写

| 模块 | 放哪 | 做什么 | 要点 |
|---|---|---|---|
| 库登记 `registry` | `core/src/registry/` + 主进程 | 应用知道有哪些库（id、文件夹、显示名、图标、颜色、排序），不再「一次只开一个」 | 登记表在 `<应用数据>\Streams\libraries.json`；库文件夹仍是自包含的（换电脑拷文件夹再「添加已有库」即可） |
| 定时与排队 `scheduler` | 主进程（用 v1.0 的 `nextRunAt / lastDueAt / missedRun`） | 每个库按自己的时间跑；错过的补一轮不叠加（v1.0 规则）；**同一时间只跑一轮**（一个队列，按到点先后），避免几个库同时打满连接 | 用量：每轮上限按库算；设置页显示全部库本月用量合计（维护者 11-05 定） |
| 主 Agent `agent` | `core/src/agent/` | 对话记录（`agent/transcript.jsonl`，正本）、局面摘要（所有库的名字 / 要求 / 待看数 / 问题 / 待定的提议）、一轮对话（发 → 收 JSON → 校验 → lookups 循环 → 落盘）、长对话压缩（超过阈值时让模型把旧对话缩成摘要，原文仍留在 jsonl） | 一次只问你一个问题（`ask` 字段只能一个，带快捷回答）；JSON 不合格式重试一次，再不行就只显示 `reply` 文本、不出卡 |
| 提议卡 `proposals` | `core/src/proposals/` | 卡的种类：建库、加来源、删 / 暂停来源、改主题与关键词、改要求、改过关线、改定时 / 上限、开跑一轮；每张卡：改什么、为什么、改前 / 改后、试抓结果（加来源时代码先试抓一次） | 状态：待定 → 确认 / 不要 / 改一下（改一下 = 把你的话带回主 Agent 重出一张）；**只有「确认」由代码执行**；每张卡和结果记进 `proposals.jsonl`（全局一份 + 相关库里一份）；执行后在库的配置旁记「主 Agent 提的 · 你确认的 · 日期」 |
| 建议卡 `suggest` | `core/src/suggest/` | **规则型**、不花模型：来源连续 N 轮被拒 / 失败、连续三轮没有产出（v1.0 已有的数）、来源出现过写给 AI 的指令、两个库的主题关键词高度重合 | 维护者 11-05 定「先不放权」：建议卡一律要你点，没有「以后这类直接做」按钮（设计稿 UC2 第 4 步那个按钮去掉）；主 Agent 可以把建议卡变成提议卡（例如替你挑一个替代来源并试抓） |
| 对话分流 `route` | `core/src/ask/route.mjs` | 库内对话框一句话 → 提问 / 改动要求 / 拿不准 | 改动要求连同库 id 交给主 Agent，提议卡回到同一个对话框里显示 |
| 阅读模式 | 主进程 + 页面 | 「打开原文」在流息里打开原网页，可切到阅读模式（抽正文） | 原网页放在隔离的 webview 里（不给 Node、不给桥）；抽正文用 `mozilla/readability`（Apache-2.0，调研已核许可证）；抽不出就退回原网页 |

### 2.3 数据放哪（新加的用 ★）

```
<应用数据>\Streams\
  settings.json          连接、主题、语言、全局开关（v1.0）；定时与上限搬到各库
  ★ libraries.json       库登记：[{ id, path, name, icon, color, order }]
  ★ agent\transcript.jsonl   主 Agent 对话正本（只追加）
  ★ agent\session.json   各连接的会话 id 缓存（丢了不要紧，靠正本重建）
  ★ agent\notes.jsonl    主 Agent 的工作区笔记（经代码写）
  ★ proposals.jsonl      所有提议卡与结果（只追加）
<每个库的文件夹>\
  notes\  index.jsonl  streams.json（★ brief / schedule / cap / setup 里多「谁定的」历史）
  _pipeline\ ledger.jsonl fetch_log.jsonl rounds.jsonl verdicts.jsonl usage.jsonl demand.jsonl …（v1.0）
  _pipeline\ ★ proposals.jsonl  ★ suggestions.jsonl
```

### 2.4 一轮怎么跑（v2）

```
定时到点（或你点「现在跑一轮」/ 你确认了「开跑一轮」的提议卡）
  → 排队（同一时间一轮）
  → 这个库：抓取（代码）→ 去重（代码）→ 关卡①②（库 Agent 调用，提示词带 brief）
  → 摘要（库 Agent）→ 核验（规则 + 判定，含「写给 AI 的话」规则）→ 待看（代码写账本）
  → 规则型建议检查（代码）→ 有新建议就进「和主 Agent 聊」的「等你定的事」和该库的概览
  → 左栏数字刷新
```

### 2.5 权限（设计稿第二节 + 维护者 11-05 答复）

| 动作 | 谁能做 | 怎么把关 |
|---|---|---|
| 写 `notes/` | 只有你（收藏、编辑、导入写头） | `writeNoteFile` 唯一入口（V2 原样）；Agent 不经点头写 notes/：**先不能**（维护者 11-05） |
| 改库的配置（来源、主题、要求、过关线、定时、上限） | 你直接改；或主 Agent 出提议卡、你确认后由代码改 | 提议卡 schema 校验 + 只认「确认」 |
| 建库 | 你，或主 Agent 提议、你确认 | 同上；文件夹位置由你选或用默认位置（写在卡上） |
| 主动做事 | 没有人：建议卡一律要你点（**先不放权**，维护者 11-05） | — |
| 执行命令 / 读写任意文件 | 没有模型能做 | 命令行一律零工具；API 连接本来就没工具 |
| 读网上内容 | 库 Agent（零工具、不留会话） | 「写给 AI 的话」规则 + 标记 |

## 五、怎么验（v2 验收标准：草案，**只有 维护者 能定**）

v1.0 的 V1–V12 大多照用（V2 只有收藏写 notes、V3 五种抓取状态、V4 无新数据零改动、V5 坏格式重试、V6 登录过期、V7 禁词、V8 待规范、V9 问库出处、V10 每轮上限、V11 签名与署名、V12 核验层）；V1 改成 v2 的用例。玄翎建议加：

| 草案 | 标准 |
|---|---|
| N1 | 主 Agent 的任何改动都必须经一张你确认过的提议卡；变异测试：去掉「只认确认」的守卫，测试必须变红 |
| N2 | 库 Agent / 问库 / 主 Agent 的命令行调用一律零工具；扫描所有调用参数 |
| N3 | 一篇含「写给 AI 的指令」的材料：条目被标记、来源与库配置零改动（UC5） |
| N4 | 三个库各自定时：错过补一轮不叠加；同一时间只跑一轮 |
| N5 | 主 Agent 会话缓存丢失（删掉 `session.json`）后，对话能从正本接着进行 |
| N6 | 设计稿五个 Use Case 在真窗口里逐步走通，截图与设计稿对照 |

## 六、风险与未核实

| 事 | 状态 | 怎么办 |
|---|---|---|
| Codex 命令行接续会话 | 未核实（本机没装 Codex） | 装上后实测；不行就和 API 一样走「流息重放对话正本」，不影响架构 |
| 主 Agent 用 JSON 动作的稳定性 | 未实测 | 包 C 第一天做真调用试验；坏格式重试一次、再坏只显示文字（不出卡、不执行） |
| 长对话的用量 | 要定 | 压缩阈值与摘要策略在包 C 定，设置里可看主 Agent 的用量 |
| 阅读模式抓原网页 | 有些站抽不出正文 | 退回原网页；原网页在隔离 webview 里 |
| 「写给 AI 的话」规则会漏 | 规则 + 判定兜底，仍可能漏 | 库 Agent 零工具是根本防线：漏了也只会影响那一条的分数 |
| 产品方案（Desktop\流息\方案）还是 v1.0 的 | 方案是 Phrolova 维护的 | 要不要让 Phrolova 把方案改成 v2，维护者 定 |
